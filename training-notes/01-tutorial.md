# 01 — In-app tutorial inventory

Prepared for the branch secretary / branch DB administrator training-of-trainers (TOT). Source: the codebase as of 2026-09-30 (`main`, commit `34b445a`). Nothing was changed in the code.

**How to read this document**

- **Narration** is copied verbatim from the narration scripts in `resources/tutorials/narration/*.txt`. Those scripts are the source the MP3 audio is generated from. The only change is that the TTS pause markers (`<break time="0.6s" />`) have been removed. Spellings such as "I-D", "D-B", "H-Q", "S-M-S" and "N-R-C-S" are there to guide pronunciation and are kept as written.
- **UI labels** are the labels as users see them in the app. Where the tutorial's wording differs from the live screen, the row says so under **⚠ Label check**. Point these out to participants so they don't hunt for a button that has a different name.
- "Slide N" follows the order the slides appear in the player (the `Slide N of M` counter).

## 1. How the tutorial system is built

| Piece | Location | What it does |
|---|---|---|
| Lesson registry | `config/tutorials.php` | Defines the 4 levels (title, icon, `min_access`) and 11 lessons (key, level, order, title, Blade view). This is the single source of lesson order and visibility. |
| Controller | `app/Http/Controllers/TutorialController.php` | `index` builds the lesson list with completion ticks. `lesson` renders one lesson (403 if the level is locked for you). `complete` records completion. `level` just redirects to the index. |
| Routes | `routes/web.php` (prefix `/learn`, names `tutorials.*`) | `GET /learn` (lesson list), `GET /learn/lesson/{key}`, `POST /learn/lesson/{key}/complete`. The pages live under `/learn` because `public/tutorials/` is the asset folder and a `/tutorials` route would collide with it (Decisions.md). |
| Progress table | migration `2026_06_11_000002_create_tutorial_progress_table.php`, model `App\Models\TutorialProgress`, `User::tutorialProgress()` | One row per user × `lesson_key` (unique), with `completed_at`. A lesson counts as **complete as soon as the user reaches the last slide**. There is no quiz. |
| Lesson content | `resources/views/tutorials/lessons/level{0,1,2,3}/*.blade.php` | Each lesson is a Blade view containing the slides. The content is code, not database data, so changing a lesson requires a deploy. |
| Slide player (Alpine.js) | `resources/views/components/tutorial/player.blade.php` | Shows one slide at a time: **Previous** / **Next** buttons, progress dots, a "Slide N of M" counter, and ←/→ keyboard keys. It also has the narration controls: a play/sound toggle (with a "Start narration" coachmark), pause/resume and replay, plus a progress bar. On the last slide it shows **Lesson completed** and a **Back to lesson list** link. Narration never autoplays. The user has to turn it on. |
| Slide components | `components/tutorial/slide.blade.php` (text slide), `split-slide.blade.php` (screenshot + steps, optionally `stacked`), `step.blade.php` (numbered step) | Each slide has an optional `data-audio` MP3. Elements marked `data-reveal` fade in one after another. |
| Narration scripts | `resources/tutorials/narration/<level>-<lesson>-<slide>.txt` (95 files) | Plain-text scripts with ElevenLabs `<break>` tags. |
| Audio | `public/tutorials/audio/*.mp3` (97 files) | Generated by `php artisan tutorials:narrate` (`app/Console/Commands/NarrateTutorials.php`, ElevenLabs TTS). The command only regenerates changed scripts, using the hash manifest `storage/app/tutorial-narration-manifest.json`. |
| Screenshots | `public/tutorials/img/*.jpg` | Used by the split slides. |
| Entry point | Dashboard → **Training** section → **Open Tutorials** | Opens `/learn`. The **Tutorials** list shows all levels. Locked levels are shown greyed out with a padlock. |
| Completion report | Dashboard → **Tutorial Completion** button → `/reports/tutorial-completion` | Lets branch and national users see who has completed which lesson. Branch users see only their own branch. Only role-holders are listed. |

There is **no** seeder, JSON content file or database table for lesson content, and no guided page-tour (driver.js). Page tours were deferred to a later phase (Decisions.md).

Visibility is decided by `User::getAccessLevel()` and each level's `min_access` list in `config/tutorials.php`:

| branch | Branch Secretary, Branch DB Administrator, Branch DB Assistant |
| division | Division DB Assistant — Finance, Division DB Assistant — Operations |
| none | anyone with no role: every level is locked |

| Level | Title on the Tutorials page | Unlocked for |

| 0 | Getting Oriented | division, branch, national |
| 1 | Level 1: Records & Reporting Basics | division, branch, national |

In the live config, **Level 2 is also open to division assistants and Level 3 is open to branch roles**. So your branch secretaries and branch DB administrators **can open the Level 3 national lesson**.

**Narration** (`level0-member_volunteer.txt`):

> In this database, every person belongs to one of three groups. A volunteer gives their time, with no fee. They serve hands-on in a Red Cross unit — emergency response, first aid, and community programmes. A volunteer and member does both. They serve as an active volunteer in a Red Cross unit, and they also register as a paying member. A supporting member supports our mission financially, without volunteering. They pay a membership fee, but they are not in a Red Cross unit. So, ask two questions: is this person in a Red Cross unit, and have they paid a membership fee? The answers tell you which group they belong to.

#### Slide 7 — Four lifecycle statuses
| Page / UI | User action |
|---|---|
| No app page. Pending engagement / Active / Dormant ("Still with us") vs Archived ("No longer with us"). | None |

**Narration** (`level0-lifecycle.txt`):

> Every person in the database has a lifecycle status. There are four. Pending engagement means the person is new. They have just registered, but they are not yet actively involved. They are waiting to be welcomed and brought on board. Active means the person is currently involved — taking part, paying, or serving. Dormant means the person has gone quiet. They are still in the system, still a member or a volunteer, but they have not been active for a while. They have not left — they may simply need to be re-engaged. Archived means the person has left the system. They are no longer counted as a member or a volunteer, and they are set aside from the active records. So, pending, active, and dormant are all "still with us" — the difference is only where the person is on their journey.

#### Slide 8 — Three kinds of group
| Page / UI | User action |
|---|---|
| No app page. Red Cross Unit (Permanent), Task Force (Temporary), Organisation (External). | None |

**Narration** (`level0-groups.txt`):

> There are three more terms to know — the groups people belong to. First, a Red Cross unit. This is the permanent volunteer group within a division. It is the home base for volunteers — they belong to a unit, and they record their activity through it. Second, a task force. A task force is a temporary group, created within a branch, but open to anyone in the database — volunteers and members alike. It might be an emergency response team, or simply a working group, like a database team. It lasts as long as you need it, and is dissolved when the work is done. Third, an organisation. An organisation is a body outside the Red Cross — a company, or an institution. You use it to keep track of memberships and donations that come from that organisation, rather than from an individual person. So: a unit is the permanent home for volunteers, a task force is a temporary group anyone can join, and an organisation is an outside body whose membership and giving you record.

**Narration** (`level1-registering-intro.txt`):

#### Slide 2 — A second person checks every record  *(four-eyes)*
| Page / UI | User action |
|---|---|

**Narration** (`level1-registering-four_eyes.txt`):

> For donations, payments, volunteering, and training, one person enters the record. But it doesn't count yet. A different person has to check it and approve it before it's final. The person who entered it can never approve their own entry — even if they normally have approval rights. It always takes a second person. And until it's approved, the record won't show up in reports, totals, or statistics.
